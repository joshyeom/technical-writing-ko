# technical-writing-ko

AI가 쓴 한글 산출물을 읽기 쉽게 다듬습니다. 파일 문서, 채팅 답변, HTML 본문, 화면 문구, 코드 주석의 한글이 대상입니다.

**마켓플레이스**: [skills.sh/joshyeom/technical-writing-ko](https://skills.sh/joshyeom/technical-writing-ko/technical-writing-ko)

## 왜 만들었나

업무에서 AI에게 글을 맡기면 세 가지가 반복됐습니다.

**출력물이 너무 많습니다.** 한 가지를 물으면 절 4개와 불릿 20개가 돌아옵니다. 길게 쓰는 것이 기본값이기 때문입니다.

**읽어도 핵심이 안 잡힙니다.** 결론이 마지막 문단에 있거나, 중요성만 말하고 수치가 없거나, `최적화를 통해 개선되었습니다`처럼 무엇을 어떻게 했는지 빠져 있습니다.

**안 쓰는 특수문자가 섞입니다.** 줄표(`—`), 꺽쇠(`「」`), 중간점(`·`), 곡선따옴표(`""`)가 한글 문장에 들어옵니다. 한국어 글쓰기에서 쓰지 않는 기호라 눈에 거슬립니다.

그런데 업무에서 읽기 편한 글은 따로 있었습니다. **테크니컬 라이팅 기법으로 쓴 글**입니다. 행동 주체를 밝히고, 추상어 대신 측정값을 쓰고, 한 문장에 생각 하나만 담는 규칙들입니다. 그 기법을 AI 산출물에 적용하려고 만들었습니다.

## 어떻게 여기까지 왔나

처음에는 Claude에게 쓰지 말 낱말 몇 개를 알려 주는 것으로 시작했습니다. 그런데 고쳐야 할 낱말이 계속 늘었고, 낱말만 바꿔도 문장 구조가 그대로면 읽기가 나아지지 않았습니다.

Codex와 같이 쓰다 보니 Codex가 윤문을 더 정확하게 하는 것이 보여서, 1차 수정을 Codex에게 맡겼습니다. 그래도 Claude로 넘어온 결과를 다시 다듬을 때 같은 문제가 남았습니다.

그래서 스킬로 만들고, 문제가 보일 때마다 규칙을 고쳤습니다. 그 뒤로 읽기가 편해졌습니다. 지금도 AI slop 범벅인 글을 보면 바로 규칙을 고칩니다.

**한계**: 이 규칙에는 작성자가 선호하는 작문 스타일이 섞여 있을 수 있습니다. 쓰기 전에 이 점을 감안하세요. 규칙 하나하나는 [`SKILL.md`](skills/technical-writing-ko/SKILL.md)에 근거와 대조 예시로 적어 두었으니, 맞지 않는 규칙은 고치거나 빼고 쓰면 됩니다.

## 무엇을 하나

**기호는 전수 제거합니다.** 줄표, 꺽쇠, 중간점, 곡선따옴표, 이중피동은 판단이 필요 없습니다. 정규식으로 모두 찾아 고치고, 최종본을 내기 전에 다시 검사해 0건을 확인합니다.

**분량을 줄입니다.** 채팅 답변은 결론을 첫 문장에 쓰고 핵심을 3개까지만 씁니다. 조사 과정과 검증 절차는 물을 때 답합니다.

**핵심이 보이게 고칩니다.** 행동하는 사람을 주어로 세우고, `상당히 개선됐다`를 근거에 있는 수치로 바꾸고, 은유 술어를 실제 동작으로 되돌립니다. 근거에 없는 내용은 지어내지 않고 `미해결`로 밝힙니다.

## 적용 범위

산출물 종류로 구분하지 않습니다. **그 글자가 사람이 읽는 한글 산문인지**로 구분합니다.

| 적용합니다 | 건드리지 않습니다 |
|---|---|
| 파일 문서(`.md`, `.html`) | 코드, 식별자, 변수명 |
| 한글 채팅 답변 | URL, 파일 경로, 명령어 |
| HTML과 JSX 안의 본문 글자 | 태그와 속성 이름 |
| 화면에 보이는 버튼, 라벨, 안내 문장 | 이미 있는 에러 문구와 로그 |
| 코드 주석의 한글 설명 | 영어로 만드는 산출물 |
| 커밋 메시지와 PR 본문의 한글 | 사용자가 확정했다고 밝힌 문구 |

같은 파일 안에서도 글자에 따라 적용 여부가 다릅니다.

```ts
// 사용자 정보를 통해 권한을 확인합니다   ->  // 사용자 정보로 권한을 확인합니다
const userId = req.params.id;            ->  그대로
```

```html
<button id="refresh">새로고침 실시</button>  ->  <button id="refresh">새로고침</button>
```

코드, URL, 경로, 명령어는 바꾸면 동작하지 않습니다. 이미 있는 에러 문구와 로그는 그 글자로 검색하므로 바꾸지 않습니다. 새로 쓰는 한글 문구는 적용합니다.

**쓰지 않아야 할 곳**: 문장이 평범해지기 때문에 은유가 장점인 칼럼, 에세이, 마케팅 글에는 쓰지 마세요. 정확성이 우선인 기술 문서, 리포트, 채팅 답변에 씁니다.

## 구조

기계가 셀 수 있는 것과 판단이 필요한 것을 나눕니다.

**Layer 1. 정규식 검사.** 줄표, 꺽쇠, 중간점, 이중피동, 곡선따옴표, 메타 담화, 번역투 조사, 접속어 뒤 쉼표, 굳은 맞춤법 오타를 `scan.sh`로 전수 처리합니다. 코드 블록과 인라인 코드는 검사에서 뺍니다. 과장어, 막연한 출처, 연출용 대조, 직역 어휘, 긴 문장은 후보로만 보여 주고 원칙으로 판단해 고칩니다. 최종본을 내기 전에 같은 스크립트를 다시 돌려 제거 대상이 0건인지 확인합니다.

**Layer 2. 원칙 리뷰.** 패턴 ID를 나열하는 대신 원칙 8개와 대조 예시를 둡니다. 목록에 없는 표현이라도 원칙에 어긋나면 고치고, 원칙에 어긋나지 않는 문장은 건드리지 않습니다.

| 원칙 | 내용 |
|---|---|
| 1 | 행동의 주체를 분명히 한다 |
| 2 | 은유 술어를 실제 동작으로 되돌린다 |
| 3 | 구체적으로 쓴다 |
| 4 | 자연스러운 한국어로 쓴다 |
| 5 | 짧게, 일관되게 |
| 6 | 상투 서두와 결말, 기계적 연결어를 지운다 |
| 7 | 연출을 뺀다 |
| 8 | 읽는 사람이 아는 말로 쓴다 |

**추측 금지.** 은유를 빼면 실제로 무슨 동작인지 빠진 부분이 생깁니다. 근거에 없으면 지어내지 않고 중립 동사로만 바꾼 뒤 `미해결`로 보고합니다.

**새 문서.** 새로 쓰는 문서는 유형(튜토리얼, 문제 해결, 참조, 설명)을 먼저 정합니다. 제목 아래 개요를 쓰고, 읽는 사람이 얻는 결과를 먼저 씁니다. 기존 문서를 다듬을 때는 구조를 바꾸지 않습니다.

## 낱말 목록 대신 판별법

은유와 직역체는 종류가 끝없습니다. 목록으로 잡으려면 사례를 계속 모아야 하고, 목록이 길어지면 매 세션 읽는 비용도 같이 늘어납니다. 그래서 질문 3개로 판단합니다.

**판별법 1 (물리 동작)**

> 술어를 손으로 하는 동작이나 물리 현상으로 떠올릴 수 있는데, 글의 주제는 물리적인 게 아니라면 은유다.

아래 비교 표의 `얹히다`, `갉아먹다`, `맞물리다`, `새어나가다`가 이렇게 잡힙니다. 어느 패턴 목록에도 없는 말입니다.

**판별법 2 (영어 되짚기)**

> 이 말을 영어로 되짚으면 원래 한 낱말이 보이는가. 보이면 그 영어를 직역한 은유다.

판별법 1은 동사만 잡습니다. 명사와 형용사로 된 은유는 물리 동작으로 떠올릴 수 없어 판별법 1에 잡히지 않습니다. `축`(axis), `결`(grain), `창`(window), `약하다`(weak)가 두 번째 질문에 잡힙니다.

**판별법 3 (흔해서 안 보이는 말)**

> 이 동사를 뜻에 맞는 동사로 바꿔 적을 수 있는가.

너무 흔한 동사는 은유인지 지나치기 쉽습니다. 분산을 `본다`, 노이즈로 `본다`, 문구를 `본다`를 한 문장에 섞어 쓰면 측정과 판정과 의심이 한 동사에 섞입니다. 동작을 구분할 수 있는데도 중립적인 동사 하나로 통일하지 않습니다.

**순우리말 직역체**도 같은 방식입니다. 그 말이 업계 문서에 그 뜻으로 쓰이는지 묻습니다. 안 쓰이고 국어사전에만 있으면 순화어입니다. 목록에 없던 `누리집`, `갈무리`, `내림목록`도 이렇게 잡힙니다.

## 문체

파일 문서의 기본은 합쇼체입니다. 아래 순서로 정하고, 위에서 정해지면 아래는 확인하지 않습니다.

1. 사용자가 말한 것 (`해요체로`, `음슴체로`)
2. 기존 문서를 손보는 경우, 원문의 어미
3. 문서 유형 (보고서는 합쇼체, 가이드는 해요체, 메모는 음슴체, 분석은 한다체)
4. 판단이 안 서면 합쇼체

파일 문서는 본문만 정한 문체를 쓰고, 표와 불릿과 라벨은 개조식으로 분리합니다. 표 셀과 라벨은 명사로 끝냅니다. `검토했습니다`나 `검토함`이 아니라 `검토 완료`라고 씁니다.

## 두 경로

| | 스킬 | 출력 문체 |
|---|---|---|
| 켜는 법 | 자연어 요청으로 자동 호출 | `/output-style`에서 `Korean Plain` |
| 대상 | 파일로 저장하는 한글 산출물 | 모든 한글 채팅 답변 |
| 스크립트 | `scan.sh`를 실행 | 실행하지 않고 읽어서 적용 |
| 분량 규칙 | 없음 | 결론 먼저, 핵심 3개까지 |
| 읽는 시점 | 스킬 호출 때 1회 (세션 내 유지) | 세션 시작 1회 |

두 파일은 같은 원칙을 공유하지만 같지 않습니다. 한쪽만 고치면 두 경로의 규칙이 달라집니다.

## 이 저장소 문서의 검사 결과

이 저장소 문서에도 같은 규칙을 적용합니다. `scan.sh`를 돌리면 아래 2개만 제거 대상으로 남고, 나머지 문서는 0건입니다. 종료 게이트 규칙에 따라 남긴 문장과 이유를 적습니다.

| 파일 | 잡히는 문장 | 남긴 이유 |
|---|---|---|
| `README.md` | 참고 절의 토스 테크 링크 | 글 제목에 든 중간점. 고유명사입니다 |
| `skills/technical-writing-ko/SKILL.md` | 원칙 4의 `Don't` 예문 | 고치면 규칙을 설명할 수 없습니다 |

### 스크립트 3개

```bash
bash self-check.sh                      # 저장소 문서가 자기 규칙을 지키는지 검사
bash compare-style.sh "프롬프트"          # 같은 질문을 문체 없이와 있이 각각 받아 비교
bash improve-loop.sh evals/_local/<사례>  # 규칙 결함을 찾아 개선안까지 만들고 멈춤
```

`self-check.sh`는 문서 6개에 `scan.sh`를 돌리고, `SKILL.md` 표가 금지한 말을 문서가 자기 목소리로 쓰는지도 확인합니다. 금지어 목록을 스크립트에 적지 않고 표에서 읽어 오므로, 표를 고치면 검사도 따라 바뀝니다. 종료 코드 0은 기계로 잡는 항목에 위반이 없다는 뜻입니다. 1이 나오면 출력에 적힌 문장을 고치거나, 의도한 예외면 위 표에 적고 스크립트의 `EXPECTED_GATE`를 고칩니다.

원칙 1, 3, 5, 6, 8처럼 맥락을 봐야 하는 항목은 이 스크립트가 검출하지 못합니다. 판별법으로 새로 잡히는 표현도 목록에 없어서 정규식으로는 검출되지 않습니다. 규칙을 고친 뒤에는 이 부분을 사람이 읽어야 합니다.

규칙을 고칠 때 지킬 것은 [`evals/README.md`](evals/README.md)에 있습니다. 채점기를 원본에 먼저 돌려 검증하기, 1회 측정으로 판단하지 않기, 규칙이 `미해결`로 남기라고 한 표현을 누락으로 세지 않기입니다. 3가지 모두 실제로 틀린 결론을 낸 경험에서 나왔습니다.
