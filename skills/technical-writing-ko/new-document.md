# 새 문서를 쓸 때

새로 쓰는 문서에만 적용한다. 기존 문서를 다듬을 때는 적용하지 않는다.

## 문서 유형을 먼저 정한다

읽는 사람이 이 문서로 무엇을 하려는지 확인하고 유형을 고른다. 유형마다 구성이 다르다.

| 유형 | 읽는 사람의 목적 | 구성 |
|---|---|---|
| 튜토리얼 | 처음 써 보면서 전체 흐름을 익힌다 | 목표, 준비물, 단계, 결과 확인 |
| 문제 해결 | 특정 문제를 풀거나 작업 하나를 끝낸다 | 문제 상황, 준비물, 해결 방법, 확인 방법 |
| 참조 | 사용법을 찾아 바로 적용한다 | 개요, 매개변수나 속성 표, 예시 |
| 설명 | 개념과 등장 배경, 동작 원리를 이해한다 | 개념 정의, 배경, 동작 원리 |

한 문서는 한 유형과 목표 하나를 중심으로 쓴다. 다른 유형의 내용이 길어지거나 핵심 주제가 2개면 문서를 나누고 링크한다.

## 문서 범위

- 제목이 4단계(`####`)까지 깊어지면 하위 내용을 별도 문서로 나눈다.
- 여러 주제를 소개해야 하면 각 문서로 연결하는 개요 문서를 따로 만든다.

## 제목 바로 아래 개요를 쓴다

개요 1~2문장에 이 문서를 읽으면 무엇을 할 수 있는지 쓴다. 배경과 역사는 개요에 쓰지 않는다.

> **Don't**  이 문서는 TypeScript의 유틸리티 타입을 소개합니다.
> **Do**  `Partial`, `Pick`, `Omit`으로 기존 타입을 고쳐 쓰면 같은 타입을 다시 선언하지 않아도 됩니다.

## 얻는 결과를 먼저 쓴다

기능 목록이나 배경보다 읽는 사람이 얻는 결과를 먼저 쓴다. 세부 설정과 배경은 그 뒤에 쓴다.

> **Don't**  이 API는 여러 설정 옵션을 제공합니다.
> **Do**  이 API를 쓰면 로그가 실시간으로 처리됩니다. 설정 옵션은 아래 표에 있습니다.

## 예측할 수 있는 순서로 쓴다

- 기본 개념, 사용법, 예시, 심화 내용 순서로 쓴다.
- 코드 예시 앞에 그 코드가 하는 일을 한 문장으로 쓴다.
- 여러 문서에서 같은 내용을 다루는 절은 같은 이름으로 부른다(`설치`와 `환경 설정`을 섞지 않는다).
- 지금 동작하는 것만 쓴다. 출시 예정인 기능은 미리 쓰지 않는다.

## 제목

- 읽는 사람이 검색할 핵심 키워드를 넣는다(`에러 해결 방법` → `NOT_FOUND_USER 에러 해결 방법`).
- 30자 안으로 쓴다.
- 같은 수준의 제목은 같은 형태로 쓴다(`설치`, `설정`, `배포`).
- 물음표와 느낌표를 쓰지 않는다.
- 절차 문서는 단계 제목에 번호를 붙인다.
