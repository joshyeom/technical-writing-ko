# technical-writing-ko

한글 기술 문서를 사람이 쓴 문서로 되돌린다.

**적용 범위**: 산출물 종류로 가르지 않는다. **그 글자가 사람이 읽는 한글 산문인지**로 가른다. 한글 산문이면 어디에 있든 적용한다. 코드 주석 안의 설명, 커밋 메시지와 PR 본문의 한글, HTML과 JSX 안의 본문 글자, 로그와 에러 문구를 새로 작성할 때가 모두 해당한다. 같은 파일 안에서도 갈린다. `const userId = ...`는 그대로 두고 그 위의 주석 `// 사용자 ID를 통해 조회한다`는 `// 사용자 ID로 조회한다`로 고친다. 한글로 만드는 산출물은 종류를 가리지 않는다. HTML과 JSX로 쓰는 문서, 화면에 보이는 버튼과 라벨과 안내 문장, 브라우저로 입력하거나 등록하는 한글 글, 데이터 파일에 담는 한글 설명이 모두 해당한다. 태그와 속성 이름은 그대로 두고 그 안의 글자를 고친다(`<p>지표를 통해 확인합니다</p>`는 `<p>지표로 확인합니다</p>`로 고친다). 코드, 식별자, URL, 파일 경로, 명령어는 바꾸면 동작하지 않으므로 그대로 둔다. 이미 있는 에러 문구와 로그는 그 글자로 검색하므로 바꾸지 않는다. 영어는 바꾸지 않는다.

**범위 밖**: 기존 문서를 다듬을 때는 문단 순서 변경, 두괄식 전환, 목차 재구성 같은 구조 재배치는 하지 않는다. 이 스킬은 문장과, 메시지 하나나 항목 하나 안의 문장 순서만 손댄다.
단, 상투 서두와 결말 삭제, 문단 연결어 정리는 재배치가 아니라 삭제라서 한다(원칙 6).
새 문서를 쓸 때는 아래 새 문서를 쓸 때 절에 따라 구조부터 정한다.

**채팅 답변**: 채팅 답변을 다듬을 때는 사용자가 어미를 따로 지정하지 않으면 원래 어미를 유지한다. 불릿, 짧은 줄, 표, 제목 서식은 그대로 두고 문장과 메시지 하나나 항목 하나 안의 문장 순서를 다듬는다. 아래 위치마다 다르게 쓴다 절의 서식 지시는 적용하지 않는다. 아래 출력 보고 형식은 생략한다. 다듬은 글은 파일로 저장한 뒤 `scan.sh`로 검사하고, 제거 대상은 모두 고치고 후보는 원칙으로 판단한다. 파일로 내지 않는 답변이면 임시 파일에 저장해 검사한다. 어미와 근거를 확인한 뒤 제거 대상을 읽어 고친다. 이어서 원칙 2(은유 술어)와 원칙 8(읽는 사람이 아는 말), 원칙 1, 3, 4, 5, 7과 한 단위 안의 순서, 원칙 6 순으로 검토한다. 보내기 전에 제거 대상과 의미 보존을 다시 확인하고, 다시 고쳤으면 재확인한다. 확인 과정이나 스캔 건수는 매 답변에 덧붙이지 않으며, 근거에서 알 수 없는 내용은 `미해결`로 밝힌다. 윤문 결과를 설명할 때는 예외로 남긴 표현과 이유도 적는다. Claude Code에서 Korean Plain 출력 문체를 켜면 이 원칙과 확인 순서가 모든 한글 채팅 답변에 적용된다. Korean Plain은 여기에 직접 쓰는 답변의 분량 규칙(결론 먼저, 핵심 3개까지)을 더한다.

## 절대 규칙

1. **의미 100% 보존.** 사실, 수치, 고유명사, 직접 인용, 주장은 한 글자도 바꾸거나 지어내지 않는다. 가능성과 확정의 강도, 부정, 비교 대상, 주장 범위도 뜻에 들어간다(`대부분의 팀은`을 `팀은`으로 줄이지 않는다). 코드, 식별자, URL, 명령어, 법령 조문은 그대로 둔다.
2. **길이 목표 없다.** "N% 이내로 고쳐라" 같은 제약은 두지 않는다. 고칠 게 많으면 많이 고친다. 대신 1번을 어기지 않는다.
3. **톤은 아래 문체 정하기 절로 결정한다.** 임의로 바꾸지 않는다.
4. **새 수사 금지.** 윤문하면서 원문에 없던 비유, 강조, 감탄을 넣지 않는다. 이 스킬은 빼는 일만 한다.
5. **사용자가 정한 표현은 그대로 둔다.** 사용자가 확정한 문구나 일부러 쓴 표현이라고 밝힌 말은 규칙에 어긋나도 고치지 않는다.

# Layer 1: 정규식 검사 (판단 없음, 전수 제거)

눈으로 세지 마라. 돌려라. 코드 블록과 인라인 코드는 빼고 본다.

이 스킬 폴더의 `scan.sh`를 돌린다.

```bash
bash ${CLAUDE_SKILL_DIR}/scan.sh <파일>
```

- `${CLAUDE_SKILL_DIR}`가 그대로 보이면(Claude Code가 아닌 에이전트) 이 SKILL.md가 든 폴더의 `scan.sh`를 쓴다.
- 종료 코드 0은 제거 대상 0건, 1은 제거 대상이 남아 있다는 뜻이다.
- 인자가 없거나 파일이 없거나 읽을 수 없거나 검사 중 오류가 나면 이유를 출력하고 종료 코드 2로 끝난다.
- 2는 검사를 끝내지 못했다는 뜻이며 통과가 아니다.
- 스크립트 내용을 복사해 직접 돌리지 않는다. 스킬 인자가 스크립트의 `$` 숫자를 바꿔 넣기 때문이다.

한국어는 활용하면 어간 끝 글자가 바뀐다(`되어지다` → `되어진다`, `되어집니다`).
위 패턴에 안 나왔다고 없는 게 아니다. **스크립트는 눈을 대신하지 않는다. 눈으로도 한 번 더 읽는다.**

제거 대상 교체:
- 줄표(`—`, `–`, 띄어 쓴 ` - `와 ` -- `) → 원문에서 두 말의 관계가 분명하면 연결어(`그래서`, `하지만`, `예를 들어`)로 잇는다. 관계가 분명하지 않으면 마침표로 나눈다. 둘 다 안 되면 쉼표나 괄호. 숫자 범위(`5–10`)는 잡지 않는다. **살려두지 않는다.**
- 꺽쇠(`「」`, `『』`) → 꺽쇠만 지운다. 법령 이름도 같다(`「산업안전보건법」 제36조` → `산업안전보건법 제36조`). 코드, 파일, 명령은 백틱으로 쓴다. 화면 문구가 문장과 섞여 헷갈릴 때만 큰따옴표로 감싼다.
- 중간점(`·`) → 조사나 쉼표로 푼다. 항목이 2개면 `사실과 수치`, 3개 이상이면 `사실, 수치, 고유명사`. 표 셀과 제목도 같다. 기호만 지워 낱말을 붙이거나 항목을 빼지 않는다.
- 이중피동 → 능동, 안 되면 단일 피동 (`판단되어진다` → `판단된다`)
- 곡선따옴표 → 곧은 따옴표
- 메타 담화 → 삭제. 대부분 지워도 문장이 성립한다. 3개 유형 모두:
  흐름 예고(`이제 ~를 살펴보겠습니다`), 불필요한 강조(`사실은`, `결론적으로`, `결론부터 말씀드리면`, `솔직히 말하면`, `정직하게 말하면`),
  독자 반응 유도(`아시다시피`).
  문장 첫머리에서 요약을 예고하는 `종합하면`, `정리하자면`도 지운다. 내용을 실제로 종합하는 문장(`두 로그를 종합하면 원인은 디스크다`)은 둔다.
- 번역투 조사 → 아래 원칙 4로
- 접속어 뒤 쉼표 → 쉼표만 지운다 (`따라서, 결과가` → `따라서 결과가`)
- 굳은 오타 → 표준 표기로 (`됐`, `돼요`, `할게`, `며칠`, `왠지`, `웬만`, `어떡해`). 외래어 표기는 원칙 5를 따른다.

후보는 Layer 2 원칙으로 판단해 고칠지 정한다. 전부 지우지 않는다. 멀쩡하면 그대로 둔다.
긴 문장 기준인 20어절은 출발점이다. 넘었다고 무조건 자르지 않는다.

**종료 게이트: 최종본을 내기 전에 `scan.sh`를 다시 돌린다. 제거 대상에 한 줄이라도 잡히면 아직 끝난 게 아니다.** 직접 인용(실제 발언, 법령 조문 원문)과 고유명사 안의 기호만 예외로 둔다. 법령 이름의 꺽쇠는 예외가 아니다. 남긴 줄은 출력의 스캔 줄에 줄 번호와 이유를 적는다.

# Layer 2: 원칙 리뷰 (판단 필요)

체크리스트가 아니다. 아래는 원칙 8개이고, 각각 왜 그런지와 대조 예시가 붙어 있다.
**예시에 없는 표현이라도 원칙에 어긋나면 고친다.** 목록에 없다고 넘어가지 마라.
반대로 원칙에 어긋나지 않는 멀쩡한 문장은 건드리지 않는다. 억지로 건수를 채우지 마라.

## 원칙 1. 행동의 주체를 분명히 한다

도구, 기술, 시스템, 추상 개념을 문장의 주어로 세우면 누가 무엇을 하는지 알기 어렵다.
기술 문서에서 행동하는 쪽은 대개 읽는 사람이다.

> **Don't**  이 스크립트는 캐시 삭제를 수행합니다.
> **Do**  이 스크립트를 실행하면 캐시가 지워집니다.

> **Don't**  이 문서가 다루는 지점은 하나다.
> **Do**  이 문서는 한 가지만 다룬다.

피동으로 행위자가 사라진 문장도 같은 문제다. 행동할 사람을 주어로 되돌린다.

> **Don't**  배포 전에 설정 파일이 검토되어야 합니다.
> **Do**  배포 전에 설정 파일을 검토하세요.

예외: 도구 자체의 동작을 설명하는 문장이라면 도구가 주어여도 된다.
(`이 큐는 두 가지 방식으로 소비된다.`)

이 예외는 주어만 허용한다. 읽는 사람이 그 도구를 모르면 처음 나올 때 무엇인지 풀어 쓴다(`동기화가` → `30분마다 도는 동기화 프로그램이`). 동사가 실제 동작을 드러내는지는 원칙 2와 3으로 따로 판단한다. 도구가 주어라는 이유로 문장 전체를 그대로 두지 않는다.

주어를 `사람`으로 뭉뚱그려 쓰지 않는다. 맥락에 맞는 역할 이름(직책, 직급, 사용자, 개발자, 담당자, 관리자)으로 쓴다. 누가 해도 되는 일이면 `누구든`, `사용자 누구나`처럼 범위를 밝힌다. `~하는 사람`, `~할 사람`처럼 동사에 `사람`을 붙여 역할을 말하지도 않는다. `검토자`, `작성자`처럼 역할 이름으로 쓴다. 역할 이름을 근거에서 알 수 없으면 사람이나 조직을 가리키는 주어를 삭제하지 말고 원문 주어를 유지한다. 이 경우 역할을 특정할 수 없다는 점을 `미해결`로 밝힌다.

> **Don't**  사람이 요청을 승인하면 배포가 시작됩니다.
> **Do**  관리자가 요청을 승인하면 배포가 시작됩니다.

## 원칙 2. 은유 술어를 실제 동작으로 되돌린다

**이 원칙이 이 스킬의 핵심이다. 다른 어떤 것보다 먼저 확인한다.**

물리적 동작을 빌려 쓴 술어는 글에 리듬을 주지만, 실제로 무슨 일이 일어나는지를 가린다.
읽는 사람마다 다르게 해석하고, 번역하면 뜻이 무너진다.

> **Don't**  에러가 발생하면 Exception을 **던집니다**.
> `throw`를 그대로 옮긴 말이라, 호출한 쪽에 전달한다는 뜻인지 그냥 오류를 낸다는 뜻인지 사람마다 다르게 읽는다.
> **Do**  에러가 발생하면 예외(Exception)를 **일으킵니다**.

> **Don't**  이 서버가 트래픽을 다 **받아낸다**.
> **Do**  이 서버가 트래픽을 다 **처리한다**.

> **Don't**  배치를 새벽에 **태운다**.
> **Do**  배치를 새벽에 **실행한다**.

**판별법 1 (물리 동작)**: 술어를 손으로 하는 동작이나 물리 현상으로 떠올릴 수 있는데,
글의 주제는 물리적인 게 아니라면 은유다. `박는다`, `쏜다`, `들고 있다`, `건넨다`, `떠받친다`,
`걷어낸다`, `삼킨다`, `탄다`, `그린다`, `연다`, `가른다`, `닫힌다`가 여기 해당한다.
목록은 예시다. 목록에 없는 동사도 처리나 실행을 물리 동작으로 표현했는지 문맥으로 판단해, 해당하면 실제 동작으로 바꾼다.

**판별법 2 (영어 되짚기)**: 판별법 1은 동사만 잡는다. 명사, 형용사, 부사로 된 은유는
물리 동작으로 떠올릴 수 없어 판별법 1로는 놓친다. 그래서 두 번째로 묻는다.
**이 말을 영어로 되짚으면 원래 한 낱말이 보이는가.** 보이면 그 영어를 직역한 은유다.
`축`(axis), `결`(grain), `층위`(layer), `창`(window), `자리`(slot), `해자`(moat), `기둥`(pillar),
`조용히`(silently), `약하다`(weak), `좁힌다`(narrow)가 이렇게 잡힌다.
실제 동작이나 뜻으로 되돌린다(`두 가지로 본다`, `방식이 다르다`, `기회가 있는 기간`,
`오류를 알리지 않고 넘긴다`, `근거가 부족하다`, `주장이 맞는 범위를 밝힌다`).

**판별법 3 (흔해서 안 보이는 말)**: 너무 흔한 동사는 은유인지 지나치기 쉽다. 문맥에서
뜻에 맞는 실제 동사로 바꿀 수 있는지 묻는다. 바꿀 수 있으면 그 동사를 쓴다. 측정,
판정, 분석, 점검처럼 동작을 구분할 수 있는데도 중립적인 동사 하나로 통일하지 않는다.
바꿀 동사가 없으면 그대로 둔다.

아래는 판별법으로 잡기 어렵거나 Claude가 특히 자주 쓰는 것만 남긴 표다.
오른쪽은 예시이고, 실제 동작은 문맥에서 확인해 고른다.

| 쓰지 않는다 | 영어 원어 | 이렇게 쓴다 |
|---|---|---|
| `원칙에 걸린다`, `규칙에 걸린다` | violate | `원칙에 어긋난다`, `규칙을 어긴다` |
| `실측한다` | measure | `직접 측정한다` |
| `미러링한다`(말투, 행동) | mirroring | `따라 한다` |
| `이 경로를 탄다` | path (처리 흐름) | `이 단계를 거친다` |
| `하중 지지`, `떠받친다` | load-bearing | `이 부분이 빠지면 동작하지 않는다` |
| `값을 박는다` | hardcode | `값을 코드에 직접 적는다` |
| `기준이 흔들린다`, `경계가 흐려진다` | shake, blur | `기준이 일정하지 않다`, `경계를 알기 어려워진다` |

예외로 그대로 쓰는 것:
- 글자 그대로의 뜻일 때 (화면의 창, GitHub 이슈, 건물 기둥, 동영상의 장면)
- 사전에 오른 쓰임 (`의견이 갈린다`, `마음이 흔들린다`)
- 기술 용어로 굳은 말 (`화면 미러링`, `렌더링`)

바꿀 때 지킬 것:
- 원문이 말한 사실만 남긴다. 은유가 흐려놓은 부분을 **추측으로 채우지 않는다.**
  무슨 동작인지 원문에서 알 수 없으면, 은유를 빼고 중립적인 동사로만 바꾼 뒤
  그 부분을 `미해결`로 보고한다. 지어내는 것보다 모른다고 적는 게 낫다.
- 관용구로 굳어 사전에 오른 표현(`발이 넓다`, `손을 보다`)은 은유로 치지 않는다.

## 원칙 3. 구체적으로 쓴다

> **Don't**  요청이 몰리면 응답이 느려질 수 있습니다.
> **Do**  초당 500건을 넘으면 응답 시간이 2초를 넘습니다.

> **Don't**  설정을 바꾸면 반영됩니다. (누가, 어디에?)
> **Do**  관리자가 설정을 바꾸면 운영 서버에 즉시 반영됩니다.

여러 단계로 이어지는 문서에서는 값의 출처와 용도를 밝힌다.
`API 키를 넣습니다`가 아니라 `키 발급 단계(2단계)에서 받은 API 키를 넣습니다`.

**단, 원문에 없는 수치를 만들어내지 않는다.** 원문이 모호하면 모호한 채로 두고 보고서에 적는다.
`가능성이 있다`, `필요할 수도 있다`, `X에 가깝다` 같은 완충 표현은 원문이 실제로 단언하고 있을 때만 단언으로 바꾼다.

- 절차는 어디서(어느 서버, 어느 화면) 하는지, 앞 단계가 무엇인지 밝힌다. 원문에 없으면 `미해결`로 남긴다.
- 막연한 출처(`연구에 따르면`, `업계에서는`)는 원문에 출처가 있으면 그 이름을 쓴다. 없으면 표현을 그대로 두고 `미해결`로 보고한다. 출처를 지어내거나 주장을 지우지 않는다.
- 필드나 값을 설명할 때는 단위와 조건별 의미를 쓴다(`duration: 세션 지속 시간` → `duration: 세션 지속 시간(밀리초). 직접 로그아웃하면 실제 이용 시간, 시간 초과로 끝나면 마지막 활동까지의 시간`). 원문에 없으면 지어내지 않고 `미해결`로 남긴다.
- 0과 1 사이 비율(`정확도 0.87`)은 퍼센트로 쓴다. 화면이나 코드에 적힌 값이 따로 있으면 괄호에 남긴다(`정확도 87%(화면 표기 0.87)`).

## 원칙 4. 자연스러운 한국어로 쓴다

영어는 동사를 명사로 바꿔 쓰는 게 자연스럽지만, 한국어는 동사 그대로가 자연스럽다.

> **Don't**  임시 파일을 정리하는 작업을 수행합니다.
> **Do**  임시 파일을 지웁니다.

> **Don't**  지표 수집 진행을 통해 큐 적체 확인 작업을 실시하게 됩니다.
> **Do**  지표를 수집해서 큐가 밀렸는지 확인합니다.

> **Don't**  관리자가 검토한 신청서를 승인으로 바꿉니다.
> **Do**  관리자가 검토한 신청서를 승인합니다.

- 근거 문서나 원문의 표현이 이 규칙에 어긋나면 사실만 가져오고 표현은 규칙에 맞게 바꿔 쓴다. 근거에 `파일을 붙여 보낸다`라고 적혀 있어도 `파일을 첨부해 보낸다`로 쓴다. 의미 보존은 사실과 주장을 지키라는 뜻이지 낱말을 그대로 두라는 뜻이 아니다. 원문에 근거와 다른 동작이나 주어가 있으면(근거에 없는 `모인다`, `생긴다`) 따라 쓰지 않고 근거대로 고친다.
- 빈 한자어 `수행`, `진행`, `실시`, `존재`는 대개 지워도 뜻이 남는다.
- `~를 통해` → `~로`, `~에 대해` → 목적격 조사로 직결(`X에 대해 논의` → `X를 논의`)
- `~에 의해` 피동 → 행위자를 주어로
- 영어 직역 틀을 푼다: `강한 경쟁력을 가지고 있다` → `경쟁력이 강하다`, `더 쉽게 만든다` → `더 쉬워진다`, `폭우로 인하여` → `폭우로`, `주말의 경우` → `주말에는`, `하나의 방법이다` → `방법이다`, `설정되어 있는 값` → `설정된 값`
- 상태 이름 뒤에 `로 바꾼다`를 붙여 상태를 바꾸는 일을 돌려 쓰지 않는다. `처리 완료로 바꾼다`는 `처리 완료한다`나 `상태를 완료로 변경한다`로 쓴다. 무엇의 상태를 바꾸는지 밝힌 `상태를 X로 변경한다`는 그대로 쓴다. `X 처리한다`는 `X한다`로 쓴다(`삭제 처리한다`는 `삭제한다`).
- 영어 동사를 옮긴 한자어는 쉬운 말로 쓴다: `탐색한다`(explore) → `살펴본다`, `기능한다`(function as) → `작동한다`, `역할을 한다`
- 이중 부정은 뜻이 같을 때만 긍정문으로 쓴다: `설정하지 않으면 안 된다` → `설정해야 한다`. `없지 않다`처럼 뜻이 달라지는 표현은 그대로 둔다.
- 어려운 행정어는 쉬운 말로 바꾼다: `상기` → `위`, `금번` → `이번`, `익일` → `다음 날`, `의거하여` → `따라`. 법령이나 계약에서 정해진 문구는 그대로 둔다.
- 사람이 아닌 것에 높임을 붙이지 않는다: `결제가 완료되셨습니다` → `결제가 완료됐습니다`. 높일 사람의 것(`말씀`, `생각`)은 그대로 둔다.

## 원칙 5. 짧게, 일관되게

- 한 문장에 생각 하나. 길면 자른다. 지시문은 한 문장에 동작 하나만 쓴다.
- 쉼표로 길게 잇지 않는다. 한 문장에 쉼표가 셋 이상이면 연결어미로 풀거나 문장을 나눈다.
- 한 문장으로 될 말을 3문장으로 늘리지 않는다. 세부를 덜어내는 건 손실이 아니라 이득이다.
  (단, 원문에 있는 **사실**은 덜어내지 않는다. 덜어낼 대상은 수식과 완충 표현이다.)
- 사실을 담지 않는 과장어(`강력한`, `원활한`, `획기적인`, `손쉽게`)와 강조 부사(`매우`, `정말`)는 지우거나 원문에 있는 측정값으로 바꾼다. 조건을 담은 말(`즉시`, `자동으로`, `만`)은 남긴다.
- 한 동작을 여러 낱말로 늘어뜨리지 않는다. 업계에서 쓰는 한 낱말이 있으면 그 말을 쓴다. `파일을 다시 한 번 내려받는 데 성공하면`은 `재다운로드에 성공하면`, `여러 장을 한 번에 보고 분류한다`는 `여러 장을 일괄 분류한다`로 쓴다.
- 한 문장에서 같은 말을 되풀이하지 않는다. `결제 취소는 취소된 뒤 환불이 끝나야 인정한다`는 `결제 취소는 환불이 끝나야 인정한다`로 쓴다.
- `~할 수 있습니다`가 반복되면 뜻이 같을 때만 동작으로 쓴다: `이 버튼으로 파일을 저장할 수 있습니다` → `이 버튼을 누르면 파일이 저장됩니다`. 가능성을 말하는 표현(`느려질 수 있습니다`)과 읽는 사람이 고르는 선택지는 둔다.
- 같은 개념은 같은 말로. (`추가`/`첨부`/`넣다`를 섞지 않는다)
- 약어는 처음 나올 때 풀어쓴다. `SSR(Server-Side Rendering)`
- 기술 용어는 공식 표기를 따른다. `K8` → `쿠버네티스(Kubernetes)`
- 외래어는 맞춤법보다 업계에서 널리 쓰는 표기를 따른다. (`프런트엔드`보다 `프론트엔드`)

## 원칙 6. 상투 서두와 결말, 기계적 연결어를 지운다

AI는 글의 유형과 무관하게 서론-본론-결론 틀을 쓴다. 어느 글에나 들어갈 수 있는
배경 설명으로 시작해, 앞 내용을 요약하고 당위로 끝낸다. 문장이 하나하나 멀쩡해도
이 틀 자체가 티다. 글의 첫 문단과 끝 문단을 반드시 본다.

**상투 서두**: 독자가 이미 알고, 이 글이 아니어도 할 수 있는 말이면 지운다.
이 글에서만 할 수 있는 판단이나 구체적 사례가 첫 문장이 되게 한다.
채팅 답변 첫머리의 맞장구(`맞습니다. 정확한 지적입니다`)도 상투 서두다. 지우고 답을 바로 쓴다.

> **Don't**  현대 사회에서 서버 모니터링은 매우 중요한 과제입니다. 본 문서에서는 알림 설정 방법을 안내합니다.
> **Do**  알림은 세 곳에서 설정합니다.

**상투 결말**: 본문을 다시 요약하는 문단, `우리는 ○○해야 합니다` 같은 당위나 교훈을 지운다.
핵심 판단이 담긴 문장에서 끝내고, 그 문장을 뒤에서 다시 풀어 설명하지 않는다.

> **Don't**  지금까지 캐시 도입 효과를 살펴보았습니다. 앞으로도 지속적인 성능 개선을 위해 노력해야 할 것입니다.
> **Do**  캐시 도입으로 응답 시간이 1.2초에서 300ms로 줄었습니다. (여기서 끝낸다)

**기계적 연결어**: 문단 첫머리의 `또한`, `한편`, `따라서`, `아울러`가 반복되면 지운다.
지운 뒤에는 앞 문단의 핵심어를 다음 문단 첫 문장이 이어받게 해서 연결한다.
논리적 귀결을 실제로 표시하는 `따라서` 하나까지 지우라는 게 아니다. 매 문단 반복이 문제다.

절대 규칙 1과의 경계: 상투 서두와 결말은 이 글에서만 할 수 있는 말이 아니므로
지켜야 할 "주장"으로 치지 않는다. 단, 그 안에 문서 고유의 사실과 수치가 섞여 있으면
그 부분만 남기고 상투구만 지운다.

## 원칙 7. 연출을 뺀다

AI는 전할 사실이 없어도 정해진 문장 틀을 쓴다. 대조, 수사 의문문, 장식용 나열이 대표적이다. 서두와 결말의 틀은 원칙 6에서 다룬다.
틀을 지우고 원문이 실제로 말하는 사실만 남긴다.

> **Don't**  이번 변경은 단순한 버그 수정이 아니라 구조 개선입니다.
> **Do**  이번 변경은 구조를 개선합니다.

> **Don't**  왜 배포가 늦어졌을까요? 원인은 승인 대기였습니다.
> **Do**  배포는 승인 대기 때문에 늦어졌습니다.

> **Don't**  이 설정은 매우 중요한 역할을 합니다.
> **Do**  이 설정은 중요합니다. (원문에 이유가 없으면 `미해결`로 남긴다)

- 대조(`X가 아니라 Y다`, `단순한 X가 아니다`, `단순히 X가 아니라 Y다`): 연출이면 Y만 쓴다. 읽는 사람이 실제로 X로 헷갈릴 만하면 남긴다(`로컬이 아니라 운영 서버에 반영됩니다`).
- 부정 나열(`X도 아니고 Y도 아니다. Z다.`): Z만 쓴다. 남길 기준은 대조와 같다.
- 수사 의문문과 예고(`왜 그럴까요?`, `생각해 보세요`): 답을 평서문으로 바로 쓴다. FAQ처럼 실제로 묻는 질문은 둔다.
- 형식 틀(`중요한 것은 X다`, `핵심은 X다`, `~라는 점에서`, `~것이다`): `X가 중요하다`처럼 주어와 술어로 바로 쓴다.
- 기계적 병렬(`첫째, 둘째, 셋째`)과 장식용 3개 나열: 순서가 뜻을 갖는 절차가 아니면 번호를 뗀다. 운율을 맞추려고 붙은 수식 항목은 뺀다. 원문의 실제 항목은 개수와 상관없이 둔다.
- 글 앞에서 개수를 말했으면(`원인은 세 가지다`) 그 개수만큼 번호 목록이나 `첫째, 둘째`로 나눠 쓴다. 읽는 사람이 항목을 세며 읽을 수 있게 한다. 말한 개수와 항목 수를 맞춘다.
- 중요성만 말하는 문장: 원문에 이유가 있으면 이유를 쓴다. 없으면 과장만 빼고 `미해결`로 남긴다.

## 원칙 8. 읽는 사람이 아는 말로 쓴다

이 문서를 처음 여는 사람이 한 번 읽고 뜻을 알아야 한다.
쓴 사람만 아는 말이 남으면 다른 원칙을 다 지켜도 읽히지 않는다.

> **Don't**  대화를 열면 훅이 브랜치로 일을 찾아 세션을 적습니다.
> **Do**  대화를 열면 Claude Code가 브랜치 이름으로 일을 찾아 이 대화를 그 일에 기록합니다. (문서 안에 훅은 Claude Code가 저절로 실행하는 스크립트, 세션은 이 대화라고 적혀 있을 때)

> **Don't**  M2에서 막히면 WP-0으로 돌아갑니다.
> **Do**  검토 단계에서 막히면 작업 계획 단계로 돌아갑니다. (문서 안에 M2는 검토, WP-0은 작업 계획이라고 적혀 있을 때)

- 처음 보는 사람이 모르는 번호와 코드(`M1`, `D-01`, `C-min`, `WP-0`)는 이름으로 바꾼다. 문서 안에 뜻이 없으면 지어내지 말고 `미해결`로 남긴다.
- 앞에서 매긴 단계나 항목 번호(`3단계`, `P5`)만으로 가리키지 않는다. 그 단계가 하는 일을 같이 쓴다 (`3단계에서 받은 키` → `키 발급 단계(3단계)에서 받은 키`).
- 읽는 사람이 모를 내부 용어(`훅`, `세션`, `캐시 키`)는 처음 나올 때 하는 일로 풀어 쓴다.
- 명사를 이어 붙인 요약(`연도 경계 수정`, `업체 저장 때 합침`)은 누가 무엇을 하면 무슨 일이 생기는지 문장으로 푼다.
- 억지로 순화한 말을 만들지 않는다. 업계에서 쓰는 말(`필터`, `버전`, `검색`)은 그대로 둔다.

### 순화어 판별법

업계 용어를 쓸 곳에 순우리말이나 영어 직역을 넣으면, 읽는 사람은 그 말을 번역한 말투로 읽는다.
낱말 목록을 외우는 대신 아래 두 가지를 물어 판단한다. 목록에 없는 말도 이걸로 잡는다.

1. **그 뜻으로 업계 문서에 나오는 말인가.** 그 분야 문서, 공식 문서, 에러 메시지에 그 말이 그 뜻으로 쓰이는지 확인한다. 안 쓰이고 국어사전에만 있으면 순화어다. `단추`, `고르개`, `본보기`, `흉내 서버`, `관문`, `원천`, `물음`, `부른다`, `꾸민다`가 여기 해당한다. 업계가 쓰는 말로 되돌린다(`버튼`, `드롭다운`, `템플릿`, `목(mock) 서버`, `게이트`, `출처`, `질문`, `호출한다`, `수식한다`).
2. **업계가 쓰는 말이라도 그 문맥의 뜻이 맞는가.** 1번을 통과해도, 같은 말이 다른 것을 가리키는 문맥에서 쓰이면 뜻이 어긋난다. 아래 표가 이 경우다.

1번은 말만 보면 판단된다. 2번은 말이 멀쩡해서 문맥을 봐야 하므로 표로 남긴다.

**1번에 걸렸는데 무엇을 가리키는지 모를 때**도 그 말을 그대로 두지 않는다. 여기서 `미해결`은 두 가지를 구분한다.
- 그 순우리말이 업계에서 뭐라고 불리는지는 아는 경우(`관문`은 게이트, `원천`은 출처, `입구`는 진입점). 이건 모르는 게 아니라 아는 것이므로 업계 용어로 바꾼다. 가리키는 대상이 문서에 안 적혀 있어도 낱말은 바꿀 수 있다.
- 그 말이 무엇을 가리키는지 추측해야 하는 경우(`뒤판`이 배경인지 딤인지, `쪽매김`이 페이지네이션인지 레이아웃인지). 이때만 낱말을 그대로 두고 `미해결`로 보고한다.

대상을 모르는 것과 업계 용어를 모르는 것은 다르다. 앞쪽이면 바꾸고, 뒤쪽이면 남긴다.

쉬운 말로 풀어 쓴다며 업계 한자어와 외래어를 바꾸지 않는다. 동사도 같다. 업계에서 쓰는 동사(`호출한다`, `수식한다`, `식별한다`)가 있으면 그 말을 쓴다. 넣는다, 고친다, 지운다, 채운다 같은 일상 동사는 그대로 둔다.

**맥락을 봐야 하는 말**. 왼쪽 말 자체는 정상이고, 괄호 안 뜻으로 쓰일 때만 오른쪽으로 고친다.

| 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| `시험`(소프트웨어 테스트) | `테스트` |
| `판`(버전, 빌드) | `신 버전`, `오늘 11시 버전` |
| `머리`(`Host 머리`) | `헤더` |
| `상자`(다이어그램 요소) | `박스`, `노드`, `카드` |
| `장면`(UI) | `화면`, `시나리오` |
| `화면`(근거 문서가 페이지라고 부를 때) | `페이지` |
| `칸`(입력 필드) | `입력란`, `필드` |
| `줄`(목록의 항목, 표의 행) | `항목`, `행` |
| `줄`(제목 줄, 버튼 줄, 탭 줄) | `헤더 영역`, `버튼 영역`, `탭 바` |
| `건`(대상을 가리킬 때) | `미처리 상담`처럼 대상 이름. 수를 세는 `11건`은 그대로 쓴다 |
| `신호` | 실제 이벤트 이름(`체크 표시`, `종료 상태`) |
| `절`(문법) | `수식어` |
| `둘`, `셋`(개수를 셀 때) | `2개`, `3개`. `둘 중 하나` 같은 관용구는 그대로 쓴다 |
| `붙는다`(첨부) | `첨부된다` |
| `읽는다`(데이터, 표시를 보고 판단할 때) | `확인한다`, `조회한다`, `분석한다` |
| `찾는다`(AI나 분석이 결과를 낼 때) | `식별한다`, `인식한다` |
| `끝남`, `기다림`, `하는 중`(상태어) | `완료`, `대기`, `진행 중` |

- 문장, 항목, 데이터 행을 `줄`로 세지 않는다: `문장 12줄` → `문장 12개`, `3줄 들어갔다` → `3건 들어갔다`. 코드, 로그, diff의 줄 수와 입력 칸의 줄 수는 그대로 `줄`로 쓴다.

- 다른 문장의 문제를 짚을 때는 그 문장을 순우리말로 풀어 말하지 않고 문제가 된 부분을 따옴표로 인용한다. `값이 스스로 바뀌는 것처럼 써서`는 `'설정값이 바뀌어'에 바꾸는 주체가 없어서`로 쓴다.

- 수는 아라비아 숫자로 쓴다 (`조사 넷` → `조사 4건`, `조건이 둘` → `조건이 2개`).
- 표 머리글과 라벨에 의문사 낱말(`무엇`, `어디`, `때`, `누가`)을 쓰지 않는다. 담긴 내용의 이름(`작업 내용`, `장소`, `일시`, `담당자`)을 쓴다.
- 버튼과 라벨에는 동작 이름만 쓴다. 조건이나 설명은 라벨에서 빼서 안내 문장으로 옮긴다 (`시끄러우면 글로 쓰기` → 라벨 `글로 쓰기`).

## 한 단위 안의 순서

문서 구조는 손대지 않지만, 메시지 하나나 항목 하나 안의 문장 순서는 아래를 따른다.
문장을 옮기기만 하고 새 사실을 넣지 않는다. 빠진 요소는 `미해결`로 보고한다.

| 유형 | 순서 |
|---|---|
| 에러 메시지 | 일어난 일, 원인, 할 일 |
| 경고와 주의 | 할 일이나 조건, 그다음 위험 |
| 사고 보고 | 시각, 영향 범위(건수나 비율), 원인, 조치. 과거형 |
| 릴리스 노트 항목 | 항목 하나에 변경 하나. 호환이 깨지는 변경은 할 일 먼저 |
| 절차 단계 | 조건이 있으면 조건 먼저(`빌드가 실패하면 로그를 연다`), 한 단계에 동작 하나 |

# 문체 정하기

**기본값은 합쇼체(`…습니다`)다.** 아래 순서로 판단하고, 위에서 정해지면 아래는 보지 않는다.

### 1순위: 사용자가 말한 것

`해요체로`, `음슴체로`, `개조식으로`, `~다체로` 같은 지시가 있으면 그대로 따른다.
문서 도중에 바꿔달라고 하면 그 지점부터가 아니라 **문서 전체**를 바꾼다.

### 2순위: 기존 문서를 손보는 경우, 원문의 어미

이미 쓰인 문서를 윤문할 때, 문서 전체가 한 어미로 일관돼 있으면 **그 어미를 유지한다.**
해요체로 쓴 가이드를 합쇼체로 바꾸는 건 문체 교정이 아니라 다시 쓰기다.

예외 두 가지:
- 어미가 섞여 있으면(`…습니다`와 `…해요`가 한 문서에 혼재) 다수 쪽으로 통일한다. 반반이면 3순위로 간다.
- 사용자가 1순위로 지시했으면 원문 어미보다 그쪽이 우선이다.

### 3순위: 문서 유형

새로 쓰는 문서이고 지시가 없으면 유형에 따라 정한다.

| 유형 | 문체 | 어미 |
|---|---|---|
| 대외 보고서, 제안서, 공식 회의자료, 협의 문서 | 합쇼체 | `…습니다` |
| 사용 가이드, 온보딩, 팀 위키, 튜토리얼 | 해요체 | `…해요` |
| 내부 메모, 슬랙 공유, 빠른 초안, 작업 로그 | 음슴체 | `…임`, `…함` |
| 연구노트, 분석 문서, 기술 블로그 | 한다체 | `…한다`, `…이다` |
| 릴리스 노트, README | 합쇼체 | `…습니다` |

### 4순위: 판단이 안 서면 합쇼체

유형이 애매하면 합쇼체로 쓴다. 가장 넓게 통하고, 나중에 다른 톤으로 바꾸기 쉽다.

## 위치마다 다르게 쓴다

문서 전체를 한 어미로 도배하지 않는다. **본문만 위에서 정한 톤을 쓴다.**

| 위치 | 문체 |
|---|---|
| 본문 문단 | 정한 톤 |
| 표 안 셀, 불릿 항목, 레이블 | 개조식 (명사 종결) |
| 제목, 소제목 | 명사구 |
| 코드 주석 | 원문 유지 |

표 셀과 레이블은 명사로 끝낸다. `…입니다`도, `…함`과 `…음` 끝맺음도 쓰지 않는다 (`검토함` → `검토 완료`).
제목을 질문형으로 쓰지 않는다 (`무엇이 바뀌나요` → `바뀐 점`).

## 표기와 서식

기존 문서를 다듬을 때는 원문에서 확인할 수 있는 정보로만 고친다. 링크 이름, 날짜, 대체 텍스트를 지어내지 않고 `미해결`로 남긴다.

- 순서가 있는 절차는 번호 목록으로, 순서가 없는 항목은 불릿으로 쓴다.
- 링크는 연결된 문서 이름으로 쓴다(`자세한 내용은 여기를 보세요` → `자세한 내용은 설치 가이드를 보세요`).
- 날짜는 월과 일이 헷갈리지 않게 쓴다(`10/11` → `10월 11일`, `2026-10-11`).
- 버튼과 메뉴 이름은 화면에 보이는 그대로 쓴다.
- 코드 예시는 복사해 바로 실행할 수 있게 쓴다. 바꿔야 할 값은 `<API_KEY>`처럼 표시한다.
- 이미지에는 대체 텍스트를 단다. 색만으로 정보를 구분하지 않는다(`빨간 항목` → `실패 항목`).

## 문체별 주의

- **합쇼체**: 길어진다. 원칙 5(짧게)를 같이 지켜야 늘어지지 않는다.
- **해요체**: 대외 보고서에서는 가벼워 보인다. 3순위 표를 벗어나 쓰지 않는다.
- **음슴체**: 문단이 길면 `…있음. …아님. …함.`이 반복돼 딱딱해진다. 3문장을 넘어가면 합쇼체를 고려한다.
- **개조식**: 항목이 끊겨서 인과와 근거가 실리지 않는다. **설득이 필요한 문단에는 쓰지 않는다.** 훑어 읽는 부분에만 쓴다.
- **한다체**: 사람에게 요청하는 문장(`~하세요`)과 섞이면 어색하다. 요청이 많은 문서에는 쓰지 않는다.

## 톤을 바꿔도 지키는 것

문체는 어미와 문장 길이만 바꾼다. **사실, 수치, 고유명사, 주장은 어느 톤에서도 그대로다.**
음슴체라고 근거를 빼거나, 개조식이라고 조건절을 지우지 않는다.

# 작업 순서

1. 원문을 읽는다. 새 문서를 쓰면 `new-document.md`를 읽고 유형과 구성을 먼저 정한다. 문체 정하기 절로 톤을 확정하고, 정한 톤을 한 줄로 밝히고 시작한다.
2. `scan.sh`를 돌린다. 제거 대상은 전부 고치고, 후보는 원칙으로 판단한다.
3. 문장마다 검토 표(`| 줄 | 원문 | 고친 안 | 근거 |`)를 먼저 만든다. 원칙 2(은유 술어)와 원칙 8(읽는 사람이 아는 말)부터 보고, 원칙 1, 3, 4, 5, 7과 한 단위 안의 순서로 이어서 검토한다. 이 두 원칙에 어긋나는 문장을 가장 많이 놓친다. 고칠 것이 없는 문장도 표에 넣고 근거 칸에 이유를 적는다.
4. 표의 고친 안대로 본문을 고친다. 표는 출력에 넣지 않는다(검토 모드가 아니면).
5. 원칙 6으로 첫 문단, 끝 문단, 문단 연결어를 검토한다.
6. `scan.sh`를 **다시** 돌린다. 제거 대상이 0건이어야 한다.
7. 원문과 나란히 놓고 확인한다: 사실, 수치, 고유명사가 그대로인가. 없던 주장이 생기지 않았는가. 긴 문서는 절마다 확인해 건너뛴 절이 없게 한다.

```
문체: [정한 톤] (사용자 지시, 원문 어미, 문서 유형, 기본값 중 무엇으로 정했는지)
스캔: 항목별 건수 (예: 줄표 N건 / 꺽쇠 N건 / 중간점 N건) → 전부 제거 (재검증 0건, 예외로 남긴 줄은 줄 번호와 이유)
후보: [잡힌 건수와 고친 건수]
원칙: [적용한 원칙 이름과 대표 사례 한 줄씩. 번호만 쓰지 않는다]
미해결: [원문이 모호해 손대지 않은 것. 없으면 생략]
```

건수를 부풀리지 마라. 고친 것만 적는다.

## 검토 모드

사용자가 검토만 요청하면(`어디가 문제인지만 봐줘`, `검토해줘`) 본문을 고치지 않고 아래 표만 낸다.

| 줄 | 원문 | 고친 안 | 근거 |
|---|---|---|---|

근거에는 스캔 항목 이름이나 원칙 이름을 적는다(번호만 쓰지 않는다). 이 문서에 없는 규칙을 지어내 인용하지 않는다.
